# 00. Methodology: how things are measured here and why you can trust these numbers

> Repository principle: **no number "off the top of my head"**. Every number in the docs comes either from
> `results/*.csv` (generated by `make bench`), from the output of `make experiments`, or from an exact formula
> given right next to it. Charts (`charts/*.png`) are built by `scripts/plot.py` from the CSVs only.

## Machine

| Parameter | Value (from `sysctl`) |
|---|---|
| CPU | Apple M4 Pro (8 P-cores + 4 E-cores) |
| L1d (P-core) | 128 KB (`hw.perflevel0.l1dcachesize`) |
| L2 (P cluster) | 16 MB (`hw.perflevel0.l2cachesize`) |
| Cache line | 128 B (`hw.cachelinesize`) |
| Page | 16 KB (`hw.pagesize`) |
| OS / compiler | macOS 27.0, Apple clang 21.0.0 |
| Benchmark flags | `-std=c11 -O2 -march=native` |

On a different machine the absolute numbers will differ. **The shape of the curves** (where Θ(n²) pulls away from Θ(n log n),
where the cache breaks down) will not. That is why every chart is labeled with its configuration.

## Two kinds of metrics

1. **Exact operation counters** (`bench_ops`, built with `-DDSA_COUNT`): number of comparisons,
   swaps, moves. They are deterministic and hardware-independent. These are what O/Ω/Θ describe.
   Unit tests check that the counters match the analytical formulas
   (e.g., selection sort makes exactly n(n−1)/2 comparisons on any input; see `tests/test_sort.c`).
2. **Time** (`bench_sort`, `bench_search`, `bench_ds`, `bench_graph`): built **without** counters
   so the increments don't distort the measurement. Median of 3–15 repetitions (the median is robust to outliers
   from the OS scheduler). Before each repetition the input is restored from a reference copy.
   Results are "consumed" through a `volatile` variable so the compiler can't eliminate the computation.

## Pitfalls I hit while measuring (and how they were fixed)

These items are part of the learning material: each one produces a wrong chart if you don't notice it.

| # | What happened | How it was detected | Fix |
|---|---|---|---|
| 1 | `clock_gettime(CLOCK_MONOTONIC)` on macOS has **1 µs** resolution: all intervals in the first run were multiples of 1000 ns | values 2000, 3000, 8000… in `graph_bfs.csv` | `clock_gettime_nsec_np(CLOCK_UPTIME_RAW)`. Measured minimum tick: 41 ns (24 MHz counter) — `src/common.c` |
| 2 | Eytzinger search with prefetch is **slower** than plain binary search (38.8 ns vs 14 ns at n=1024) | anomaly on the chart | the prefetch at `b + 16k` went far past the end of the array, onto not-yet-mapped pages (the cause is inferred from the fact that clamping the address removes the effect; page walks were not measured directly). Clamping the index to n → 6.1 ns. Both versions remain in the benchmark (`eytzinger` and `eytzinger_unclamped`) so the effect is visible |
| 3 | AoS vs SoA showed only 1.3× | 1 accumulator: the `s += x` loop is bound by **FP-add latency** (a dependency chain), not by memory | 4 independent accumulators → 3.0–3.3× across runs (`experiments/ex_struct_padding.c`) |
| 4 | Linear stack growth (+64, +1024) via `realloc` did **not** show the expected Θ(n²) | flat line on the chart | `experiments/ex_realloc_inplace.c` showed that macOS grows large blocks **in place** (the address doesn't change, 4–13 µs across runs vs 0.2–25 ms for copying) instead of copying. Added a variant with explicit `malloc+memcpy` — there Θ(n²) is clearly visible |
| 5 | `sort_bubble` (with early exit) on random data is 1.8× **slower** than the naive version, even though comparisons and swaps are the same (134 119 632 vs 134 209 536 comparisons, 66 733 552 swaps in both at n=16384) | `sort_time.csv`, `sort_ops.csv` | This is a code-generation effect, not an algorithmic one, and it was **proven** by an accidental control experiment: after adding an `i == j` check to `swp()` (it never fires for bubble; the logic is unchanged), at n ≤ 1024 the ratio **flipped** (n=256: naive 113 vs bubble 44 ns/elem; was 52 vs 49), while at n ≥ 4096 it stayed ~1.8× (n=16384: 3 537 vs 6 252). The microarchitectural cause (branch misses) was **not measured**: PMU counters on macOS require root |

## My own predictions that measurements refuted

I'm keeping them here on purpose: this is the best illustration of why every claim in this repository is verified.

| Prediction (before measuring) | What the measurement showed | Where |
|---|---|---|
| Bucket sort on input with 8 distinct values degrades to Θ(n²) | **no**: 7.2 ns/elem at n = 4M. All keys in a bucket are equal, and insertion sort with `>` does no shifts at all | [11-sorting](11-sorting.md) |
| `realloc` on macOS "remaps pages without copying" | **no, more precisely**: the block isn't moved at all, it is grown in place (same address) | `ex_realloc_inplace` |
| Insertion sort is faster than merge sort up to n ≈ 64 | the crossover is between 128 and 256 (13.93 vs 14.40 ns/elem at n = 128; 23.30 vs 16.18 at n = 256) | `ex_small_n_crossover` |
| Heap sort is the slowest of the n log n sorts | at n = 2M it is faster than quick_hoare_mid, quick_3way, quick_lomuto_last, libc qsort and Shell | `sort_time.csv` |
| Shell (Ciura) ≈ n^1.25 comparisons | the local exponent decreases from 1.32 to 1.10 | `sort_ops.csv` |
| The "n·log₂n" line on the chart is a lower bound for sorting | **wrong**: the lower bound is log₂(n!) = n·log₂n − 1.44n + O(log n); merge at 0.96·n·log₂n does not violate it | `charts/sort_ops.png` |

## Methodology defects found by an independent code review (fixed, data regenerated)

| Defect | Impact on the published number | Fix |
|---|---|---|
| Keys for interpolation search were an arithmetic progression a[i] = 2i | "2 comparisons, 1.6 ns" instead of the real 11.6 comparisons and 29.6 ns (n = 2²⁰) | sorted uniformly random keys; the progression is kept as a separate `arithmetic` dataset |
| Random edges with duplicates and self-loops; CSR stored duplicates, the matrix did not | the conclusion "CSR is 7× faster even on a complete graph" was wrong: on a complete graph they are actually equal | simple-graph generator |
| Swapping an element with itself was counted as a swap | the `swap` column in `sort_ops.csv` for quicksort was inflated (Lomuto on sorted 1024: 524 799 "swaps", while the real number is 0) | `swp(i, i)` is not counted |
| Different search algorithms got different key samples | comparisons between algorithms in `search_ops.csv` were on different data | one index sample per n |
| Array traversal at n = 256 took ~40 ns — one timer tick | `array,256` = 0.16 ns/elem — an artifact | the pass is repeated until ≥ 100 µs; the footprint in the CSV is now real (16 B per node) |
| `sort_merge` on small chunks measured `malloc` | the insertion/merge crossover was partly the cost of the allocator | added `merge_prealloc` |

Library bugs found by the same review — `eval_postfix` (signed overflow, negative exponent,
4·10⁸ iterations for `9^(9^9)`), `stack_push_grow_linear(k = 0)` (heap overflow), `tree_inorder_iterative`
(cap did not bound the output). All fixed, each has a regression test (`test_review_regressions`, `test_inorder_cap`).

## Run-to-run variance (measured, not assumed)

After a full benchmark regeneration (`make bench`), compared with the previous run on the same machine:

| Metric | Variance | Conclusion |
|---|---|---|
| Exact counters (`sort_ops`, `search_ops`, skip list steps, tree heights) | 0 — deterministic (fixed seeds) | these numbers reproduce bit for bit |
| Large n in sorting, BFS at V ≥ 4096, AVL/BST, heap, stack growth | usually 1–8 % | conclusions are stable |
| Small measurements (< 1 µs per run: BFS at V = 1024, search at n = 16, traversal of 256 elements) | up to 2–3× | for small n a range is quoted, not a single number |
| Eytzinger at 64 MB | **bimodal**: ~50 or ~75 ns (7 runs) | cause not established; the Eytzinger conclusion relies on n = 2²⁰ (stable) |

Verification tool: `scripts/doc_facts.py` prints every number from `results/*.csv` that the documentation
references; a `diff` of its output before and after `make bench` shows which texts need updating.

## What was NOT measured and why

- **Hardware counters** (cache misses, branch misses) — unavailable without root on macOS. Where an explanation
  relies on the cache, it is backed by *the shape of the curve relative to the L1/L2 sizes*, not by a counter.
- **Core pinning**: macOS doesn't let you pin a thread to a P-core. Long runs almost certainly run
  on P-cores, but this is not guaranteed; the median reduces the impact.
- **Energy consumption, multithreading** — outside the scope of the notes.
