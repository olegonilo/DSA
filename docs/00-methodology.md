# 00. Методика: як тут міряють і чому цим числам можна вірити

> Принцип репозиторію: **жодного числа «з голови»**. Кожне число в документах походить або з
> `results/*.csv` (згенерованих `make bench`), або з виводу `make experiments`, або з точної формули,
> яка наведена поруч. Графіки (`charts/*.png`) будуються скриптом `scripts/plot.py` тільки з CSV.

## Машина

| Параметр | Значення (з `sysctl`) |
|---|---|
| CPU | Apple M4 Pro (8 P-ядер + 4 E-ядра) |
| L1d (P-ядро) | 128 КБ (`hw.perflevel0.l1dcachesize`) |
| L2 (кластер P) | 16 МБ (`hw.perflevel0.l2cachesize`) |
| Кеш-лінія | 128 Б (`hw.cachelinesize`) |
| Сторінка | 16 КБ (`hw.pagesize`) |
| ОС / компілятор | macOS 27.0, Apple clang 21.0.0 |
| Прапорці бенчмарків | `-std=c11 -O2 -march=native` |

На іншій машині абсолютні числа будуть іншими. **Форма кривих** (де Θ(n²) відривається від Θ(n log n),
де ламається кеш) — ні. Тому кожен графік підписаний конфігурацією.

## Два типи метрик

1. **Точні лічильники операцій** (`bench_ops`, збирається з `-DDSA_COUNT`): кількість порівнянь,
   обмінів, переміщень. Вони детерміновані й не залежать від заліза. Саме їх описують O/Ω/Θ.
   Юніт-тести перевіряють, що лічильники збігаються з аналітичними формулами
   (наприклад, selection sort робить рівно n(n−1)/2 порівнянь на будь-якому вході; див. `tests/test_sort.c`).
2. **Час** (`bench_sort`, `bench_search`, `bench_ds`, `bench_graph`): збираються **без** лічильників,
   щоб інкременти не спотворювали вимір. Медіана з 3–15 повторів (медіана стійка до викидів
   від планувальника ОС). Перед кожним повтором вхід відновлюється з еталонної копії.
   Результати «з'їдаються» через `volatile`-змінну, щоб компілятор не викинув обчислення.

## Пастки, на які я натрапив під час вимірювань (і як вони виправлені)

Ці пункти — частина навчального матеріалу: кожен з них дає хибний графік, якщо його не помітити.

| # | Що сталося | Як виявлено | Виправлення |
|---|---|---|---|
| 1 | `clock_gettime(CLOCK_MONOTONIC)` на macOS має роздільність **1 мкс**: усі інтервали в першому прогоні були кратні 1000 нс | у `graph_bfs.csv` значення 2000, 3000, 8000… | `clock_gettime_nsec_np(CLOCK_UPTIME_RAW)`. Виміряний мінімальний тік: 41 нс (24 МГц лічильник) — `src/common.c` |
| 2 | Eytzinger-пошук з prefetch **повільніший** за звичайний бінарний пошук (38.8 нс проти 14 нс при n=1024) | аномалія на графіку | prefetch на `b + 16k` виходив далеко за кінець масиву, на ще не відображені сторінки (причина — висновок з того, що обмеження адреси усуває ефект; page walk-и прямо не вимірювались). Обмеження індексу до n → 6.1 нс. Обидві версії лишились у бенчмарку (`eytzinger` і `eytzinger_unclamped`), щоб ефект було видно |
| 3 | AoS vs SoA показав лише 1.3× | 1 акумулятор: цикл `s += x` обмежений **затримкою FP-додавання** (ланцюжок залежностей), а не пам'яттю | 4 незалежні акумулятори → 3.0–3.3× між прогонами (`experiments/ex_struct_padding.c`) |
| 4 | Лінійний ріст стеку (+64, +1024) через `realloc` **не** показав очікуваного Θ(n²) | рівна лінія на графіку | `experiments/ex_realloc_inplace.c` показав: macOS розширює великі блоки **на місці** (адреса не змінюється, 4–13 мкс у різних прогонах проти 0.2–25 мс на копіювання), а не копіює. Додано варіант з явним `malloc+memcpy` — там Θ(n²) видно чітко |
| 5 | `sort_bubble` (з раннім виходом) на випадкових даних у 1.8× **повільніший** за наївний, хоча порівнянь і обмінів однаково (134 119 632 vs 134 209 536 порівнянь, 66 733 552 обмінів в обох при n=16384) | `sort_time.csv`, `sort_ops.csv` | Це ефект кодогенерації, а не алгоритму, і це **доведено** випадковим контрольним експериментом: після додавання в `swp()` перевірки `i == j` (для bubble вона ніколи не спрацьовує, логіка не змінилась) при n ≤ 1024 співвідношення **перевернулось** (n=256: naive 113 vs bubble 44 нс/елем; було 52 vs 49), а при n ≥ 4096 лишилось ~1.8× (n=16384: 3 537 vs 6 252). Мікроархітектурну причину (branch-miss) **не виміряно**: лічильники PMU на macOS потребують root |

## Мої власні прогнози, які виміри спростували

Залишаю їх тут навмисно: це найкраща ілюстрація, чому в цьому репозиторії кожне твердження перевіряється.

| Прогноз (до виміру) | Що показав вимір | Де |
|---|---|---|
| Bucket sort на вході з 8 різними значеннями деградує до Θ(n²) | **ні**: 7.2 нс/елем при n = 4M. У кошику всі ключі однакові, і insertion sort з `>` не робить жодного зсуву | [11-sorting](11-sorting.md) |
| `realloc` на macOS «переносить сторінки без копіювання» | **ні, точніше**: блок не переноситься взагалі, а дорощується на місці (адреса та сама) | `ex_realloc_inplace` |
| Insertion sort швидший за merge sort до n ≈ 64 | межа між 128 і 256 (13.93 vs 14.40 нс/елем при n = 128; 23.30 vs 16.18 при n = 256) | `ex_small_n_crossover` |
| Heap sort — найповільніший серед n log n | при n = 2M він швидший за quick_hoare_mid, quick_3way, quick_lomuto_last, libc qsort і Shell | `sort_time.csv` |
| Shell (Ciura) ≈ n^1.25 порівнянь | локальний показник степеня спадає від 1.32 до 1.10 | `sort_ops.csv` |
| Лінія «n·log₂n» на графіку — нижня межа для сортувань | **неправильно**: нижня межа — log₂(n!) = n·log₂n − 1.44n + O(log n); merge з 0.96·n·log₂n її не порушує | `charts/sort_ops.png` |

## Дефекти методики, знайдені незалежним код-рев'ю (виправлено, дані перегенеровано)

| Дефект | Вплив на опубліковане число | Виправлення |
|---|---|---|
| Ключі для interpolation search — арифметична прогресія a[i] = 2i | «2 порівняння, 1.6 нс» замість реальних 11.6 порівняння і 29.6 нс (n = 2²⁰) | відсортовані рівномірно-випадкові ключі; прогресію лишено окремим набором `arithmetic` |
| Випадкові ребра з дублікатами й петлями; CSR зберігав дублікати, матриця — ні | висновок «CSR у 7× швидший навіть на повному графі» хибний: насправді на повному графі вони рівні | генератор простого графа |
| Обмін елемента з самим собою рахувався як swap | стовпець `swap` у `sort_ops.csv` для quicksort завищений (Lomuto на відсортованих 1024: 524 799 «обмінів», а реальних — 0) | `swp(i, i)` не рахується |
| Різні алгоритми пошуку отримували різні вибірки ключів | порівняння між алгоритмами в `search_ops.csv` були на різних даних | одна вибірка індексів на n |
| Обхід масиву при n = 256 займав ~40 нс — один тік таймера | `array,256` = 0.16 нс/елем — артефакт | повтор проходу до ≥ 100 мкс; footprint у CSV тепер реальний (16 Б на вузол) |
| `sort_merge` у малих шматках виміряв `malloc` | точка перетину insertion/merge частково — вартість аллокатора | додано `merge_prealloc` |

Баги в бібліотеці, знайдені тим самим рев'ю, — `eval_postfix` (знакове переповнення, від'ємний показник степеня,
4·10⁸ ітерацій для `9^(9^9)`), `stack_push_grow_linear(k = 0)` (heap overflow), `tree_inorder_iterative`
(cap не обмежував вихід). Усі виправлено, на кожен є регресійний тест (`test_review_regressions`, `test_inorder_cap`).

## Розкид між прогонами (виміряно, а не припущено)

Після повного перегенерування бенчмарків (`make bench`) порівняно з попереднім прогоном на тій самій машині:

| Метрика | Розкид | Висновок |
|---|---|---|
| Точні лічильники (`sort_ops`, `search_ops`, кроки skip list, висоти дерев) | 0 — детерміновані (фіксовані seed) | ці числа відтворюються біт у біт |
| Великі n у сортуваннях, BFS при V ≥ 4096, AVL/BST, купа, ріст стеку | зазвичай 1–8 % | висновки стабільні |
| Малі виміри (< 1 мкс на прогін: BFS при V = 1024, пошук при n = 16, обхід 256 елементів) | до 2–3× | для малих n цитується діапазон, а не одне число |
| Eytzinger при 64 МБ | **бімодально**: ~50 або ~75 нс (7 прогонів) | причину не встановлено; висновок про Eytzinger спирається на n = 2²⁰ (стабільний) |

Інструмент для перевірки: `scripts/doc_facts.py` друкує кожне число з `results/*.csv`, на яке посилається
документація; `diff` виводу до і після `make bench` показує, які тексти треба оновити.

## Що НЕ вимірювалось і чому

- **Апаратні лічильники** (cache-miss, branch-miss) — недоступні без root на macOS. Там, де пояснення
  спирається на кеш, воно підкріплене *формою кривої відносно розмірів L1/L2*, а не лічильником.
- **Прив'язка до ядра**: macOS не дає закріпити потік за P-ядром. Довгі прогони майже напевно йдуть
  на P-ядрах, але це не гарантовано; медіана зменшує вплив.
- **Енергоспоживання, багатопотоковість** — поза межами конспекту.
