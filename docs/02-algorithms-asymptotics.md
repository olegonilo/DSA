## Парадигми

- **Divide and conquer** (P1-19, **помилка** в конспекті «breaks down the algorithm … in different methods»):
  1) *розділити* задачу на менші підзадачі **того ж типу**; 2) *розв'язати* їх рекурсивно;
  3) *об'єднати* результати. Приклади в репозиторії: `sort_merge`, `sort_quick_*`, `search_binary_recursive`.
- **Greedy** (P1-21, **помилка**: «дуже рідко дає оптимум»): жадібний алгоритм оптимальний, коли
  задача має *властивість жадібного вибору* й *оптимальну підструктуру* (CLRS §16.2). Так розв'язуються
  коди Хаффмана, мінімальне остовне дерево (Крускал/Прим), найкоротші шляхи без від'ємних ваг (Дейкстра),
  вибір заявок, дробовий рюкзак. Не оптимальний — для 0/1-рюкзака, розміну монет у довільній системі.

## Асимптотичні позначення — точні визначення (CLRS §3.1)

Для функцій f, g : ℕ → ℝ≥0:

| Позначення | Визначення | Сенс |
|---|---|---|
| f = O(g) | ∃ c > 0, n₀: 0 ≤ f(n) ≤ c·g(n) ∀ n ≥ n₀ | верхня межа |
| f = Ω(g) | ∃ c > 0, n₀: 0 ≤ c·g(n) ≤ f(n) ∀ n ≥ n₀ | нижня межа |
| f = Θ(g) | ∃ c₁, c₂ > 0, n₀: c₁·g(n) ≤ f(n) ≤ c₂·g(n) ∀ n ≥ n₀ | точна межа; Θ ⇔ O і Ω одночасно |

### Головна концептуальна помилка конспекту

Конспект (P1-29, P1-34) стверджує: «**Ω описує best case, Θ — average case, O — worst case**».
Це **неправильно**, і це найпоширеніша помилка на співбесідах.

- **O / Ω / Θ** — це типи *меж* для функції.
- **best / average / worst** — це *яку функцію* ми аналізуємо: T_best(n) = min по входах розміру n,
  T_worst(n) = max, T_avg(n) = матсподівання при заданому розподілі.

Будь-яку з трьох функцій можна оцінити будь-якою межею. Приклад із виміряними лічильниками
(`results/sort_ops.csv`, n = 16384):

| Insertion sort | Функція | Виміряно (порівнянь) | Точна оцінка |
|---|---|---|---|
| best (відсортований) | T_best(n) = n − 1 | 16 383 | **Θ(n)** |
| average (випадковий) | ≈ n²/4 | 66 749 931 (n²/4 = 67 108 864) | **Θ(n²)** |
| worst (зворотний) | n(n−1)/2 | 134 209 536 = 16384·16383/2 | **Θ(n²)** |

Тобто «worst case insertion sort = Θ(n²)» і «best case = Θ(n)» — обидва твердження з Θ.
А «insertion sort = O(n²)» (без уточнення випадку) — правильне, але неточне твердження про всі випадки.

![sort_ops](../charts/sort_ops.png)

*Права панель: cmp/n² для різних (алгоритм, вхід) сходиться до констант 1/4 і 1/2 — це і є
«константа, яку ховає Θ». Ліва: cmp/(n·log₂n) для n log n-алгоритмів; пунктир — інформаційна нижня межа
log₂(n!) для будь-якого порівняльного сортування. Merge sort (0.96 при n=2¹⁸) майже на ній.*

### Інші неточності розділу

- «n is steps required to execute program» (P1-31, **помилка**): n — *розмір входу*, f(n) — кількість кроків.
- Діаграма й визначення Θ розміщені під заголовком «Omega» (P1-30), а розділ Omega повторено на p.17.
- «Space complexity = Auxiliary space + Input size» (P1-N2): додається *пам'ять, яку займає вхід*, а не «розмір».
  Більшість джерел і співбесід під «space complexity» мають на увазі **лише допоміжну пам'ять** — треба вказувати конвенцію.

## Експеримент: асимптотика vs константи

Асимптотика каже, що буде при n → ∞. На реальних n вирішують константи і пам'ять:

- `insertion` (Θ(n²)) швидший за merge sort (Θ(n log n)) до n = 128 включно, а при n = 256 уже повільніший
  (`experiments/ex_small_n_crossover.c`, merge з наперед виділеним буфером: n=64 — 9.37 проти 12.52 нс/елем,
  n=128 — 13.93 проти 14.40, n=256 — 23.30 проти 16.18; межа між 128 і 256 однакова в обох прогонах). Тому реальні сортування перемикаються на insertion
  для малих підмасивів (`quick_median3` робить це для ≤ 17 елементів). `malloc` буфера на кожен виклик
  (`merge_topdown`) помітно шкодить лише при n ≤ 16 (n=4: 11.43 проти 7.07 нс/елем).
- `heap` робить ~1.8·n·log₂n порівнянь (в 1.9 раза більше за merge) і має гірший доступ до пам'яті.
  Тому при n = 4M він повільніший за `merge_topdown` (51.8 vs 40.3 нс/елем, `sort_time.csv`).
